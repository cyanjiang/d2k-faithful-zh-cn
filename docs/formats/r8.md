# R8 / R16 image containers and palettes

Parser: `src/formats/r8.cpp`, `src/formats/palette.cpp`. Viewer:
`d2k-tool r8-info <file> [--list]` and `d2k-tool r8-sheet <file> <out.png> --palette Data/bin/PALETTE.BIN`.

These findings come from byte analysis of the 1.06 data. Each claim was
checked by parsing every file exactly to its end and by rendering contact
sheets that look correct (terrain, infantry, cursors, effects).

## Container

There is no file header and no index. A file is a flat run of entries, and an
image's **sprite number is its position** in the file. Empty placeholder
entries keep the numbering stable.

### Entry

| Off | Type | Field |
|---:|---|---|
| 0  | u8  | type: 0 = empty (the entry is just this 1 byte), 1 = image, 2 = image (see palettes) |
| 1  | u32 | width |
| 5  | u32 | height |
| 9  | i32 | offset_x: a signed hotspot. Every drawer places the image at (x − offset_x, y − offset_y): units and buildings (`FUN_00428e30`, `FUN_00427d50`), font glyphs (`FUN_0042dc00`). 1,080 DATA.R16 entries have offset_x < 0 |
| 13 | i32 | offset_y |
| 17 | u32 | image handle (runtime pointer left by the authoring tool; ignore) |
| 21 | u32 | palette handle (0 = none) |
| 25 | u8  | bits per pixel: 8 or 16 |
| 26 | u8  | frame height (logical frame the image sits in) |
| 27 | u8  | frame width |
| 28 | u8  | padding (0) |
| 29 | …   | pixels: width·height bytes (8 bpp) or width·height u16 LE (16 bpp) |

If **type = 1 and palette handle ≠ 0**, a palette block follows the pixels:
u32, u32 runtime handle, then 256 × u16 **RGB555**. That is 520 bytes. The
first u32 varies (1, 32, 252, …); nothing reads it: the loader and the blit
use only the pointer at +4.

The loader is `SetTImageToResource` (`FUN_00460550`):
- pixel data follows only when the image handle is nonzero;
- a type-1 entry with a palette handle stores its palette as the current
  one (`0x79556c`); a missing palette pointer is the "Invalid palette"
  error;
- a **type-2 entry takes the current palette**, the one of the last type-1
  entry that carried a palette ("Invalid NULL palette" if there is none).
- On a 565 screen (`0x798384` = 0xFBCE) it converts both the 16-bit pixels
  and the palette from 555 to 565 in place (`(p & 0xFFC07FC0) << 1 |
  p & 0x1F001F`), so both are stored as 555.

### Pixel formats

- 8 bpp: palette indices. With blit flags (1, x), index 0 is transparent:
  `FUN_0042fac0` writes the destination pixel into palette entry 0 and, with
  flags (1, 1), the halved destination `(dst & mask) >> 1` into entry 1,
  then writes `palette[index]`. (So entries 0 and 1 of a shared palette hold
  the last pixel of the last keyed blit.)
- 16 bpp: **RGB555** (`xRRRRRGGGGGBBBBB`). Verified: every BLOXBASE.R16 pixel
  matches the PALETTE.BIN colour of the same pixel in BLOXBASE.R8, within
  rounding.
- Embedded palettes are **RGB555**, like the pixels (the loader converts
  both with the same mask; docs/re/11-sidebar.md). An earlier note here said
  565; that was wrong.
- 16-bit images with flags (1, 1): `0xF81F` (565 magenta) is skipped and
  `0x001F` is the shadow. The shadow write keeps only the low byte,
  `(byte)(dst >> 1) & 0xEF` (a `MOVZX DX, DL` at 0x42feaf). The only 16-bit
  image in 1.06 with an `0x001F` pixel is DATA.R16 entry 5024, the sidebar
  progress buffer (`0x789194`) whose pixels the game overwrites before
  drawing, so the quirk never shows.

The game shipped two data sets: `*.R8` for 8-bit display mode and `*.R16` for
16-bit mode. `DATA.R16` keeps many sprites as 8-bit images with their own
palettes (2,472 type 1 + 2,621 type 2). We render from R16 (decided
2026-10-03, CLAUDE.md §10).

## Files (1.06)

| File | Entries | Contents |
|---|---:|---|
| DATA.R8 / DATA.R16 | 6,555 (1,450 empty) | units, buildings, infantry, effects, UI bits |
| BLOX*.R8 / .R16 | 800 each | 32×32 terrain tiles per tileset (BASE, BAT, BGBS, ICE, TREE, WAST, XMAS[R8 only]) |
| MOUSE.R8 / .R16 | 265 | cursors |
| UI_ENG.R8 / .R16 | special | 15 controls of (i32 x, i32 y) screen position + 3 entries, then 10 bare entries (positions on the 640×400 screen). Layout and use: docs/re/07 |
| UIBB.R8 / .R16 | special | 256,000 / 512,000 bytes = raw 640×400 at 8 / 16 bpp (555), no header: the whole in-game backdrop (verified, docs/re/07) |

## Palette: `Data/bin/PALETTE.BIN`

768 bytes: 256 × RGB, 6-bit VGA components (max 63). It is the main game
palette for 8-bit data. Only the 8-bit display mode loads it
(`FUN_0046aa00`, called only when the depth is 8, 0x4485c9). The exe
programs DirectDraw with each component `<< 2` (`FUN_004a3f50`, peFlags 4),
so 63 becomes 252; our tools do the same (`vga6_to_8`).
